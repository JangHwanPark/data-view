# 브랜치 전략

data-view는 박자오한(GitHub `janghwanpark`)과 Claude가 같이 만든다. 이 문서는 어느 브랜치에서 무엇을 하고, 커밋에 누구를 남기는지 정한다. 28단계부터 따른다.

## 지킬 것(집 작업 규칙, PLAN.md 0절)

- 회사 데이터 파일, 기획서, 회사 도구가 만든 폴더, 회사 테이블 이름과 실제 값은 어느 브랜치에도 올리지 않는다. 시험은 `npm run fixtures`의 가짜 데이터로만 한다.
- 코드를 회사로 옮기는 것은 정보보안실이 정한 방법으로만 한다. 옮기는 기준은 `main`의 태그다.

## 브랜치

| 브랜치 | 하는 일 | 누가 바꾸나 |
| :--- | :--- | :--- |
| `main` | 안정판. 회사로 옮길 수 있는 상태만 둔다. 태그 `v0.N`으로 옮긴 판을 표시한다 | `develop`을 합칠 때만(박자오한이 확인하고 합침) |
| `develop` | 통합. 끝나고 시험한 단계가 모인다. 로컬 서버(데모)는 보통 여기서 띄운다 | 단계 브랜치를 합칠 때만 |
| `stage/NN-주제` | 계획의 한 단계(예: `stage/28-terms`, `stage/29-qa-high`). `develop`에서 갈라 시작한다 | Claude와 박자오한 둘 다 |
| `fix/주제` | 단계와 상관없는 고침(예: `fix/sidebar-hydration`). `develop`에서 가른다 | 둘 다 |
| `docs/주제` | 문서만 바꿀 때 | 둘 다 |
| `feat/file-source` | 1~27단계를 쌓은 예전 작업 브랜치. 27단계 끝 = `main`, `develop`의 시작점. 더 쓰지 않는다 | 없음(기본 브랜치를 바꾼 뒤 지워도 됨) |

## 흐름

1. `develop`에서 단계 브랜치를 만든다: `git switch develop && git pull && git switch -c stage/29-qa-high`
2. 단계 브랜치에서 구현하고, 타입 검사, 린트, 빌드, 브라우저 확인(가짜 데이터)을 한 뒤 커밋하고 푸시한다.
3. 단계 브랜치 → `develop` 풀 리퀘스트를 연다. 박자오한이 화면과 바뀐 줄을 보고 합친다(검토도 기여다). Claude는 요청받았을 때 풀 리퀘스트를 열고, 검토 의견을 고친다.
4. 몇 단계가 모여 회사에서 써 볼 만하면 `develop` → `main` 풀 리퀘스트를 열고, 합친 뒤 `v0.N` 태그를 붙인다. 그 태그를 정보보안실 방법으로 회사에 옮긴다.
5. 합친 단계 브랜치는 지운다. 회사에서 쓰다 급히 고칠 것은 `main`에서 `fix/주제`를 갈라 `main`과 `develop` 둘 다에 합친다.

## 커밋에 남기는 사람

- 작성자(author)는 박자오한(`janghwanpark`, 계정 메일)으로 한다. 이 저장소의 git 설정 `user.name`, `user.email`에 둔다.
- Claude가 같이 만든 커밋은 메시지 끝에 `Co-Authored-By: Claude …`와 `Claude-Session: …` 줄을 붙인다. GitHub에서 두 사람이 함께 만든 커밋으로 보인다.
- 박자오한이 혼자 고친 커밋에는 Claude 줄을 붙이지 않는다.
- 메시지는 한국어로, 첫 줄은 `28단계: 용어 통일`, `고침: …`, `문서: …` 꼴로 쓴다.

## 지금 상태와 남은 설정

- `main`, `develop`은 27단계 끝(`d54fa84`)에서 만들었다. 28단계는 `stage/28-terms`, 이 문서는 `docs/branch-strategy`에 있다.
- GitHub 저장소 설정에서 기본 브랜치를 `feat/file-source`에서 `develop`(또는 `main`)으로 바꾸는 것은 저장소 주인이 한다. `main`, `develop`에 바로 푸시하지 못하게 막는 규칙(브랜치 보호)도 같은 곳에서 켠다.
