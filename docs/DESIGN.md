# data-view 설계

## 1. 개요

data-view는 내 PC에서만 실행하는 데이터 시각화 도구다. MySQL/MariaDB, Qdrant 같은 데이터베이스에 연결하거나 엑셀/CSV 파일을 열어서 표와 차트로 본다. 로그인과 배포는 고려하지 않고, `localhost`에서 Next.js 서버를 띄워 브라우저로 접속하는 형태로 쓴다.

만드는 이유는 회사에서 데이터베이스 내용을 엑셀 파일 여러 개로 받는 데 있다. 테스트하면서 값 하나를 확인하려면 주문 파일에서 고객ID를 보고, 고객 파일을 열어 그 ID를 찾고, 다시 다른 파일로 넘어가는 식으로 파일을 체이닝해야 한다. 이 과정에서 파일을 여러 개 띄워야 하고 어디까지 따라왔는지 헷갈린다. data-view는 파일 사이의 키 관계를 한 번 정해 두고, 값을 클릭해서 따라가거나 합친 표로 보거나 관계 전체를 그림으로 볼 수 있게 해서 이 과정을 한 화면 안에서 끝내는 것을 1순위 목표로 둔다. 차트와 DB 연결은 그다음이다.

사용자는 각자 자기 PC에서 실행한다. 같은 구조의 갱신본 엑셀을 자주 받기 때문에, 관계 설정은 저장해 두었다가 파일만 교체해도 그대로 적용되어야 하고, 동료와 나눌 수 있도록 파일로 내보내고 가져올 수 있어야 한다.

기준으로 삼는 데이터는 게임 기획 테이블처럼 복잡하게 얽힌 구조다. 한 번에 50~300개 시트를 다루고, 아이템, 보상, 퀘스트, 스킬 같은 테이블이 서로를 여러 방식으로 가리킨다. 단일 ID 열만이 아니라 `reward_id_1`~`reward_id_5`처럼 번호 붙은 여러 열, `1001|1002|1003`처럼 한 칸에 여러 ID, `reward_type`에 따라 가리키는 테이블이 달라지는 타입+ID 조합까지 다룬다(4.8). 파일, 데이터베이스, 벡터 DB를 사이드바에서 골라 같은 방식으로 들여다본다.

테이블 데이터만 보여주면 사내 GDF와 다를 게 없다. data-view가 따로 있어야 하는 이유는 기획서와 데이터를 잇는 데 있다(4.11). 현실의 기획서는 최신화가 안 되어 있고, 기획서에 적힌 테이블 이름이 실제로는 없거나 다른 이름인 경우가 많다. 그래서 기획서 속 이름을 실제 테이블과 이어 주는 추론, 기획서와 데이터가 다른 곳 찾기, 기획서와 데이터 사이의 양방향 이동, 기획서 기준 테스트 항목 만들기를 둔다. 추론은 규칙 기반으로만 하고, 기획서와 데이터는 PC 밖으로 보내지 않는다.

내부 툴이라 꾸밈보다 한 화면에 많은 정보를 담는 쪽을 택한다. 지금의 단색 위주 디자인은 유지하고, 글자와 행 높이를 작게 써서 표, 열 정보, 연결 패널을 한꺼번에 볼 수 있게 한다(6장).

정해진 결정은 다음과 같다.

| 항목 | 결정 |
| --- | --- |
| 사용자 | 게임 QA 엔지니어. 게임과 기획 용어는 알지만 컴퓨터 공학(키, 관계, 스키마, DB)은 모른다(1.1) |
| 사용 형태 | 로컬 전용, 각자 자기 PC, 인증 없음 |
| 핵심 기능 | 엑셀 간 키 관계 정의, 값 따라가기, 값 검색, 관계 다이어그램, 합친 표 |
| 기준 데이터 | 게임 테이블 수준. 시트 50~300개, 네 가지 참조 방식(4.8) |
| 화면 | 왼쪽 사이드바 + 정보 밀도 높은 본문, 현재 디자인 유지 |

| 스택 | Next.js App Router + TypeScript |
| 데이터 소스 (v1) | MySQL/MariaDB, Qdrant, 엑셀/CSV |

| 벡터 DB 기능 | 컬렉션 통계, 메타데이터 표/차트, 임베딩 2D 산점도, 유사도 검색 |

### 1.1 사용자

쓰는 사람은 테스트를 진행하는 게임 QA 엔지니어다.

| 안다 | 모른다 |
| --- | --- |
| 게임 콘텐츠와 시스템(퀘스트, 보상, 아이템, 가챠, 상점, 이벤트) | 데이터베이스, 키, 외래키, 관계, 스키마, 정규화 |
| 기획서를 읽고 테스트 항목을 만드는 일 | SQL, 환경변수, .env, 포트, JSON |
| 엑셀(시트, 행, 열, 필터, 찾기) | "도메인", "소스", "매칭", "후보", "일치율", "null" 같은 말 |
| 테이블에 ID가 있고 다른 테이블이 그 ID를 쓴다는 것 | ID가 이어지는 방식(번호 붙은 열, 한 칸 여러 ID, 타입+ID)의 이름 |

그래서 화면은 다음을 지킨다.

- **게임과 엑셀의 말로 쓴다.** 공학 용어는 화면에 내지 않는다. 꼭 필요하면 게임 예시로 풀어 쓴다(아래 용어 대응표).
- **질문에서 시작한다.** QA가 실제로 하는 질문("이 ID는 무엇이고 어디에 쓰이나", "기획서 숫자와 데이터가 맞나", "패치 전후로 뭐가 바뀌었나", "없는 ID를 가리키는 곳이 있나")을 첫 화면의 입구로 둔다. 기능 이름(관계, 합친 표)으로 찾게 하지 않는다.
- **판단은 앱이 하고, 근거는 숫자로 보여준다.** "값 99.7% 일치" 대신 "3,000개 중 2,991개가 맞음, 9개는 없는 ID"처럼 개수로 쓰고, 없는 ID는 눌러서 바로 볼 수 있게 한다.
- **설정은 숨긴다.** 데이터베이스 접속, 환경변수, 연결 내보내기/가져오기, 용어집 편집처럼 개발자나 담당자가 한 번 해 두면 되는 일은 "고급" 아래로 옮긴다.
- **오류는 할 일로 쓴다.** "환경변수를 읽지 못했습니다" 대신 "DB 접속 정보를 찾지 못했습니다. 개발팀에서 받은 접속 정보를 직접 입력해 주세요."처럼 다음 행동을 적는다.

#### 첫 화면

지금 첫 화면은 "데이터 소스" 목록이다. QA에게는 무엇을 할 수 있는지가 먼저 보여야 하므로, 파일을 불러온 뒤의 첫 화면을 질문 입구로 바꾼다.

```
무엇을 확인할까요?
[ ID로 찾기        ] 아이템 ID, 퀘스트 ID를 넣으면 어느 테이블의 무엇이고 어디에 쓰이는지 보여줍니다.
[ 기획서와 맞춰 보기 ] 기획서의 테이블 이름, ID, 수치가 데이터와 맞는지 봅니다.          (13단계, 표의 값 비교 완료)
[ 없는 ID 찾기      ] 다른 테이블에 없는 ID를 쓰는 곳을 모읍니다.                      (15단계)
[ 패치 전후 비교     ] 새로 받은 파일과 이전 파일을 비교합니다.                          (14단계)
[ 시스템 지도       ] 테이블이 어떤 시스템으로 묶이고 서로 어떻게 이어지는지 봅니다.
```

아직 없는 기능은 "준비 중"으로 두고 지금 있는 기능으로 가능한 만큼 연결한다(예: 없는 ID 찾기는 지금도 테이블별 연결의 "맞지 않는 ID" 개수로 시작할 수 있다).

## 2. 아키텍처

실행 단위는 Next.js 프로세스 하나다. 브라우저와 Next.js 서버가 같은 PC에 있다는 점을 전제로 역할을 나눈다.

브라우저는 화면, 차트 렌더링, 파일 데이터 처리를 맡는다. 엑셀과 CSV는 DuckDB-WASM에 테이블로 올려서 SQL로 집계한다. 파일이 서버를 거치지 않으니 업로드 크기 제한이나 서버 저장소를 신경 쓸 필요가 없다.

Next.js 서버(Route Handler)는 외부 DB 접속을 대신한다. 브라우저에서 MySQL에 직접 붙을 수 없고, 접속 정보를 브라우저에 두지 않기 위해서다. Qdrant는 REST라 브라우저에서도 호출할 수 있지만 CORS 설정과 API 키 노출을 피하려고 같은 방식으로 서버를 거친다. 앱 자체의 설정(연결 정보, 저장한 차트, 대시보드)도 서버가 로컬 SQLite 파일에 저장한다.

```
브라우저
  화면 / 차트(ECharts) / 표
  DuckDB-WASM  <- 엑셀, CSV, Qdrant payload 샘플
  Web Worker   <- PCA, UMAP 투영
      |
      | fetch (localhost)
      v
Next.js 서버 (127.0.0.1)
  /api/sources/*    연결 정보 CRUD
  /api/mysql/*      스키마 조회, 쿼리 실행
  /api/qdrant/*     컬렉션, scroll, query
  app.db (SQLite)   연결 정보, 차트, 대시보드
      |
      +--> MySQL / MariaDB
      +--> Qdrant
```

## 3. 데이터 소스 공통 모델

차트와 표 컴포넌트가 데이터 소스 종류를 몰라도 되도록, 모든 조회 결과를 같은 형태로 맞춘다.

```ts
type ColumnType = 'string' | 'number' | 'boolean' | 'date' | 'unknown';

interface QueryResult {
  columns: { name: string; type: ColumnType }[];
  rows: unknown[][];
  rowCount: number;
  truncated: boolean; // 행 제한에 걸렸는지
  elapsedMs: number;
}
```

소스별로 할 일은 테이블 목록 조회, 컬럼 스키마 조회, 쿼리 실행 세 가지이고 결과를 위 형태로 돌려준다. 공통 인터페이스 파일은 MySQL과 파일 소스 두 구현이 생기는 시점에 만든다. 처음부터 플러그인 구조를 만들지는 않는다.

### 3.1 엑셀/CSV

CSV는 DuckDB의 `read_csv_auto`로 바로 읽는다. 엑셀은 SheetJS로 시트를 읽어 행 배열로 바꾼 뒤 DuckDB 테이블로 넣는다. 시트 하나가 테이블 하나가 되고, 테이블 이름은 `파일명_시트명`을 정리한 값으로 한다. SheetJS는 npm 레지스트리 버전이 오래되어 있어서 공식 CDN 배포본(cdn.sheetjs.com)으로 설치한다.

파일은 새로고침해도 다시 열 필요가 없도록 원본을 OPFS(Origin Private File System)에 복사해 두고, 앱이 열릴 때 DuckDB에 다시 등록한다. 첫 행을 헤더로 쓸지, 타입 추론 결과를 바꿀지는 파일을 열 때 미리보기 화면에서 고른다.

파일 선택 창 말고 경로를 적어 불러올 수도 있다. 서버가 폴더(하위 폴더 제외)나 파일 경로의 엑셀, CSV, 기획서 목록을 읽고, 고른 파일만 브라우저로 넘긴다. 정해 둔 확장자 밖의 파일은 목록에도 넣지 않고 내용도 넘기지 않는다. 원본 경로를 기억해 두어, 갱신본을 같은 자리에 덮어쓴 뒤 "원본 경로에서 다시 읽기" 한 번으로 교체한다. 서버가 127.0.0.1에서만 열리고, 다른 사이트에서 이 API를 부르는 요청은 Origin을 보고 막는다.

DuckDB-WASM은 브라우저 전용이라 `'use client'` 컴포넌트에서 동적 import로만 불러오고, 인스턴스는 앱 전체에서 하나만 쓴다.

### 3.2 MySQL/MariaDB

서버에서 `mysql2/promise` 커넥션 풀을 소스별로 하나씩 만들어 재사용한다. 스키마는 `information_schema.TABLES`, `information_schema.COLUMNS`에서 읽는다.

v1에서는 MySQL 테이블을 브라우저의 DuckDB로 불러와 스냅샷으로 다룬다. 연결하면 서버가 테이블 목록과 행을 읽어 넘겨주고, 브라우저가 파일과 같은 방식(소스마다 스키마 하나)으로 DuckDB에 적재한다. 이렇게 하면 관계, 따라가기, 합친 표, 갱신본 비교(4.9)를 파일과 DB에 같은 코드로 쓸 수 있다. 소스 화면의 "다시 불러오기"로 최신 상태를 다시 읽고, 불러온 시각을 보여준다. 테이블마다 최대 20만 행까지만 불러오고 잘렸으면 표시한다. DB에 직접 SQL을 보내 실시간으로 조회하는 기능은 차트 빌더 단계에서 붙인다.

DB 접속 정보는 보통 환경변수에 들어 있으므로, 앱의 환경변수와 경로를 적은 `.env` 파일에서 찾아 바로 연결할 수 있게 한다. `DB_HOST`, `GAME_DB_HOST`처럼 DB 접두어가 붙은 HOST, PORT, USER, PASSWORD, NAME 묶음과 `DATABASE_URL=mysql://...` 꼴을 알아본다. 비밀번호는 서버 밖으로 보내지 않고 화면에는 "있음/없음"만 보여준다.

접속 정보는 서버의 `data/connections.json`에 두고, 비밀번호는 AES-GCM으로 암호화한다. 키는 `.env.local`의 `APP_SECRET`을 쓰고, 없으면 처음 저장할 때 `data/secret.key`를 만들어 쓴다. `data/`는 git에서 제외한다. 앱 설정이 연결 정보뿐이라 SQLite 대신 JSON 파일로 시작하고, 차트와 대시보드를 저장할 때 8장의 app.db로 옮긴다.

조회 전용 도구이므로 쓰기를 막는 장치를 세 겹으로 둔다. 연결 화면에서 읽기 전용 계정 사용을 안내하고, 서버에서 SELECT, SHOW, DESCRIBE, EXPLAIN, WITH로 시작하지 않는 문장과 여러 문장을 한 번에 보내는 요청을 거부하며, 세션마다 `SET SESSION TRANSACTION READ ONLY`를 건다. 결과 행은 기본 10,000행에서 자르고 `truncated`로 알린다. 쿼리 타임아웃은 30초로 둔다(`max_execution_time`, MariaDB는 `max_statement_time`).

### 3.3 Qdrant

서버에서 `@qdrant/js-client-rest`를 쓴다. 기능별로 쓰는 API는 아래와 같다.

| 기능 | 사용하는 API | 처리 위치 |
| --- | --- | --- |
| 컬렉션 통계 | getCollections, getCollection, count | 서버에서 조회 후 화면 표시 |
| 메타데이터 표/차트 | scroll (with_payload) | 서버가 payload를 평탄화해 QueryResult로 반환, 브라우저 DuckDB에 적재 |
| 2D 산점도 | scroll (with_vector, with_payload) | 브라우저 Web Worker에서 투영 |
| 유사도 검색 | query (포인트 ID 또는 벡터) | 서버 조회, 결과는 표와 산점도 강조 |

컬렉션 통계 화면에는 포인트 수, 인덱싱된 벡터 수, 상태, 벡터 설정(차원, 거리 함수, named vector 목록), payload 인덱스를 보여준다.

메타데이터는 payload를 `a.b.c` 형태의 컬럼으로 평탄화한다. 배열은 JSON 문자열로 둔다. 이렇게 하면 엑셀과 같은 DuckDB 경로를 그대로 타기 때문에 차트 빌더를 따로 만들 필요가 없다. 컬렉션 전체가 아니라 scroll로 가져온 샘플(기본 10,000건)이 대상이라는 점은 화면에 표시한다.

산점도는 벡터를 최대 5,000건 샘플링해서 2차원으로 줄인다. 기본은 PCA이고 UMAP(umap-js)을 선택할 수 있다. UMAP은 수천 건에서 수 초 이상 걸릴 수 있어서 Web Worker에서 돌리고 진행 상태를 보여준다. 점 색은 payload 필드 하나로 구분하고, 점에 마우스를 올리면 ID와 payload를 보여준다. named vector가 여러 개면 어떤 벡터를 쓸지 고른다.

유사도 검색 입력은 v1에서 포인트 ID와 원본 벡터(JSON 배열) 두 가지다. 텍스트로 검색하려면 컬렉션을 만들 때 쓴 것과 같은 임베딩 모델이 있어야 하므로 v1 범위에서 뺀다. 결과는 점수 순 표로 보여주고, 산점도에서는 해당 점을 강조한다. PCA는 새 벡터도 같은 축으로 투영할 수 있어서 샘플에 없던 결과도 표시할 수 있다. UMAP일 때는 샘플에 포함된 점만 강조한다.

## 4. 테이블 관계와 체이닝

이 프로젝트의 핵심 기능이다. 파일들은 같은 값을 가진 키 컬럼으로 이어진다(예: 주문 파일의 고객ID와 고객 파일의 ID). 컬럼 이름은 파일마다 다를 수 있다고 본다.

### 4.1 관계 모델

관계는 "어느 테이블의 어느 컬럼이 다른 테이블의 어느 컬럼을 가리킨다"는 한 줄짜리 정보다. 아래는 5단계까지 구현한 단일 열 모델이고, 게임 테이블의 여러 참조 방식을 위해 4.8에서 가리키는 쪽을 넓힌다.

```ts
interface TableRef {
  sourceId: string;
  table: string;
}

interface Relation {
  id: string;
  from: TableRef & { column: string }; // 참조하는 쪽 (주문.고객ID)
  to: TableRef & { column: string };   // 참조되는 쪽 (고객.ID)
}
```

관계는 파일 목록과 같이 OPFS의 `relations.json`에 저장한다. 파일 소스가 전부 브라우저에 있으므로 관계도 같은 곳에 둔다. DB 소스와 파일 사이의 관계는 v1 범위에서 뺀다.

### 4.2 관계 만들기

수동으로 만들 때는 테이블 두 개와 컬럼 두 개를 고른다. 저장 전에 "참조하는 쪽 값 중 몇 %가 참조되는 쪽에 있는지"와 "참조되는 쪽 컬럼이 유일한지"를 DuckDB로 계산해 보여준다. 키를 잘못 고른 경우를 바로 알아차리게 하려는 목적이다.

자동 추천은 이름이 달라도 찾을 수 있도록 값 기준으로 한다. 각 테이블에서 값이 유일한 컬럼을 키 후보로 잡고, 다른 테이블의 타입이 맞는 컬럼 중 고유값의 대부분(기본 90% 이상)이 그 키 후보에 들어 있는 컬럼을 추천한다. 이름이 비슷하면(id, _id, 코드 같은 접미사 제거 후 일치) 순위를 올린다. 추천은 사용자가 확인해야 관계로 저장된다.

값만 보면 1부터 매긴 번호 키(1, 2, 3...)에 수량 같은 작은 정수 열이 우연히 다 들어가는 오탐이 생긴다. 키가 빈틈없는 정수 연번이고 이름도 맞지 않는 추천은 버리지 않고 "가능성 낮음"으로 접어서 따로 보여준다. 가리키는 쪽 열도 유일한 값이고 이름이 맞지 않으면 행 번호끼리 겹친 경우로 보고 추천하지 않는다.

### 4.3 갱신본 교체

같은 구조의 갱신본을 자주 받으므로 소스에 "파일 교체" 기능을 둔다. 교체하면 소스 id는 그대로 두고 원본 파일만 바꿔 다시 적재한다. 관계는 소스 id, 테이블 이름, 컬럼 이름으로 대상을 가리키기 때문에 구조가 같으면 그대로 살아남는다. 이를 위해 엑셀 테이블 이름은 파일명을 빼고 시트 이름만 쓰고, CSV 테이블 이름은 실제 파일명이 아니라 처음 열 때의 소스 이름에서 만든다. 교체 후 관계가 가리키는 테이블이나 컬럼이 없어졌으면 그 관계에 경고를 표시한다.

관계 설정은 JSON으로 내보내고 가져올 수 있게 한다. 가져올 때는 소스를 파일 이름으로 맞추고, 맞는 파일이 없으면 사용자가 고르게 한다.

### 4.4 값 클릭으로 따라가기

표에서 관계가 걸린 컬럼의 값은 링크처럼 보이게 한다. 클릭하면 오른쪽에 연결된 테이블의 해당 행이 열린다. 방향은 양쪽 다 지원한다. 주문.고객ID를 누르면 고객 행 하나가, 고객.ID를 누르면 그 고객을 가리키는 주문 행들이 나온다. 열린 패널 안에서 다시 값을 누르면 다음 패널이 이어서 열리고, 위쪽에 지나온 경로(주문 #123 > 고객 C-01 > 주소 ...)를 보여준다. 여러 엑셀을 번갈아 여는 대신 한 화면에서 가로로 이어 보는 구조다. 경로는 URL 쿼리에 넣어 새로고침이나 공유 후에도 같은 위치를 연다. 경로를 바꿀 때는 `router.push` 대신 `window.history.pushState`를 쓴다. 조회가 모두 브라우저 안에서 끝나므로 단계마다 서버에 요청할 이유가 없고, 뒤로 가기로 이전 단계로 돌아갈 수 있다.

값 비교는 관계 일치율 계산과 같이 문자열 기준이다. 다만 누른 값이 숫자면 DOUBLE 열에서 800이 '800.0'으로 바뀌는 경우를 위해 숫자로도 한 번 더 비교한다. 날짜 열을 키로 쓰는 경우는 v1에서 고려하지 않는다.

### 4.5 값 검색

값 하나(예: 고객ID C-01)를 입력하면 열려 있는 모든 테이블의 모든 컬럼에서 그 값이 나오는 행을 찾아 테이블별로 묶어 보여준다. 기본은 정확히 일치이고, 포함 검색은 옵션으로 둔다. 결과 행에서 바로 4.4의 따라가기로 넘어갈 수 있다. 쿼리는 테이블마다 `CAST(컬럼 AS VARCHAR) = 값`을 OR로 묶어 DuckDB에서 실행한다.

### 4.6 관계 다이어그램

테이블을 상자로, 관계를 화살표로 그린다. 상자에는 테이블 이름, 행 수, 키 컬럼을 보여주고, 상자를 누르면 그 테이블 미리보기로 간다. 그리기는 React Flow(@xyflow/react)로 하고 배치 위치는 OPFS의 `diagram.json`에 저장한다. 저장된 위치가 없는 테이블은 관계 방향으로 층을 나눠 가리키는 쪽을 왼쪽, 가리켜지는 쪽을 오른쪽에 놓는다. 기본으로는 관계가 걸린 열만 보여주고, "모든 열 보기"를 켜면 전체 열이 나온다. 다이어그램에서 열의 오른쪽 점을 다른 열의 왼쪽 점으로 끌어 이으면 일치율을 보여준 뒤 확인을 받아 관계로 저장한다.

### 4.7 합친 표

시작 테이블을 고르고 관계를 따라 붙일 테이블을 차례로 고르면 LEFT JOIN으로 이은 한 표를 만든다. 이미 붙은 어느 테이블에서든 이어 붙일 수 있고, 가리켜지는 쪽을 붙이면(주문에 고객) 행 수가 그대로지만 가리키는 쪽을 붙이면(고객에 주문) 한 행이 여러 행으로 늘 수 있어서 선택지에 그렇게 표시한다. 조합은 URL 쿼리에 둔다.

컬럼 이름이 겹치면 `테이블.컬럼`으로 구분한다. 붙일 값은 있는데 상대 테이블에서 찾지 못한 행은 맨 앞 "연결 누락" 열에 어느 테이블에서 못 찾았는지 적고, 단계별 누락 행 수를 위에 보여준다. "연결 안 된 행만 보기"로 그 행만 걸러 데이터 누락을 찾는 데 쓴다.

결과는 SheetJS로 엑셀 파일로 내보낸다. 화면에는 앞의 1,000행만 보여주지만 내보내기는 엑셀 한 시트 한도(1,048,575행)까지 전체를 쓴다. 날짜 열은 엑셀에서 날짜로 다룰 수 있게 날짜 셀로 쓰고, 시간대 때문에 날짜가 밀리지 않도록 UTC 기준으로 넣는다.

### 4.8 게임 테이블의 참조 방식

게임 테이블은 다른 테이블을 네 가지 방식으로 가리킨다. 4.1의 관계는 첫 번째만 다루므로 가리키는 쪽(from)을 넓힌다.

| 방식 | 예 | from 설정 |
| --- | --- | --- |
| 단일 ID 열 | `item_id = 1001` | `columns: ["item_id"]` |
| 번호 붙은 여러 열 | `reward_id_1`~`reward_id_5` | `columns: ["reward_id_1", ..., "reward_id_5"]` |
| 한 칸에 여러 ID | `rewards = "1001\|1002\|1003"` | `columns: ["rewards"], separator: "\|"` |
| 타입+ID 조합 | `reward_type = ITEM`, `reward_id = 1001` | `columns: ["reward_id"], when: { column: "reward_type", value: "ITEM" }` |

```ts
interface FromSide extends TableRef {
  columns: string[]; // 1개면 단일 열, 2개 이상이면 번호 붙은 열 묶음
  separator?: string; // 한 칸에 여러 ID가 들어 있을 때 구분자
  when?: { column: string; value: string }; // 이 조건인 행만 이 관계로 본다
}

interface Relation {
  id: string;
  from: FromSide;
  to: ColumnRef; // 가리켜지는 쪽은 언제나 열 하나
}
```

타입+ID 조합은 타입 값마다 관계를 하나씩 만든다. `reward_type`이 ITEM이면 아이템 테이블, CURRENCY면 재화 테이블을 가리키는 관계 두 개가 같은 `reward_id` 열을 공유하는 식이다. 기존 `from.column` 하나짜리 관계는 읽을 때 `columns: [column]`으로 바꿔서 그대로 쓴다.

조회는 가리키는 쪽 값을 한 줄에 하나씩 펼친 뒤 비교하는 식으로 통일한다. 번호 붙은 열은 `UNNEST([c1, c2, ...])`로, 한 칸 여러 ID는 `UNNEST(string_split(CAST(c AS VARCHAR), 구분자))`로 펼치고, 빈 값은 버린다. `when`이 있으면 펼치기 전에 그 조건으로 행을 거른다. 일치율, 따라가기, 값 검색, 합친 표가 모두 이 펼친 값을 기준으로 동작한다.

화면에서는 한 칸에 여러 ID가 있으면 ID마다 따로 링크를 건다. 타입+ID 열은 행의 타입 값에 따라 링크 대상이 달라지고, 어느 관계에도 맞지 않는 타입이면 링크를 걸지 않는다. 합친 표에서 여러 값을 가진 관계를 붙이면 값 수만큼 행이 늘어나므로, 선택지에 "한 행이 여러 행으로 늘 수 있음"을 표시한다.

자동 추천도 넓힌다. 이름이 `접두어_숫자` 꼴로 같은 접두어를 가진 열이 두 개 이상이면 묶음 후보로 보고 묶음 전체의 일치율을 계산한다. 값 표본에 `|`, `,`, `;`가 자주 나오는 문자열 열은 구분자 후보로 보고 쪼갠 값으로 일치율을 본다. 한 열의 값이 키 후보 여러 개에 나눠 맞고, 같은 테이블의 값 종류가 적은 열이 그 갈라짐과 맞아떨어지면 타입+ID 후보로 보고 타입 값마다 관계를 추천한다.

### 4.8.1 테이블마다 자동으로 찾는 연결

실무 테이블은 이미 서로 이어져 있으므로, 사용자가 관계 화면에서 하나하나 잇기 전에도 테이블을 열면 이어진 테이블을 보여준다. 전체 테이블을 한꺼번에 비교하는 추천(4.2)은 시트가 많으면 느리므로, 테이블을 열 때 그 테이블의 열만 검사한다.

가리키는 쪽은 열 이름이 다른 테이블의 키 열 이름과 같거나(`reward_group_id` → RewardGroup), `_id` 같은 꼬리를 뗀 열 이름이 테이블 이름과 같은 경우(`grade_id` → Grade)다. 가리켜지는 쪽은 이 테이블의 키 열 이름이나 테이블 이름 + `_id`를 열로 가진 다른 테이블이다. 키 열 이름 앞에 쓰임새가 붙은 열(`sell_currency_id` → Currency, `free_reward_group_id` → RewardGroup)과 번호 붙은 열(`bonus_item_id_1` → Item)도 같은 키를 가리키는 것으로 본다. 여러 키에 걸리면 가장 긴 키 이름을 고른다. 키 이름이 `id`, `no`, `code`처럼 흔한 말이면 뒤쪽 일치는 보지 않는다. `key`는 다국어 문자열 테이블의 키라서 본다(`name_key` → String). 키 열은 첫 열이 98% 이상 유일하면 키로 본다(실제 데이터에는 실수로 들어간 중복 키가 섞여 있곤 해서다).

후보는 값이 90% 이상 맞을 때만 연결로 본다. 일치율은 고유값 기준과 행 기준 중 높은 쪽을 쓴다. 등급(6개)처럼 값 종류가 적은 테이블은 깨진 ID가 몇 개만 섞여도 고유값 기준 일치율이 크게 떨어지기 때문이다(등급 6개와 깨진 ID 24개면 고유값 기준 20%, 행 기준 99%).

같은 데이터를 파일과 DB로 둘 다 연 경우를 위해, 이름이 같은 테이블(복사본)은 후보에서 빼고 같은 소스, 같은 종류(파일끼리, DB끼리), 그 밖의 순서로 찾는다. 자동 연결은 점선과 "자동" 표시로 저장한 관계와 구분하고, 그 자리에서 관계로 저장할 수 있다. 값 따라가기(4.4)도 자동 연결로 동작한다. 결과는 데이터가 바뀔 때까지 테이블별로 기억한다.

### 4.9 테스트를 돕는 탐색 기능

값 하나를 찾는 일은 사내 GDF로도 할 수 있으므로, data-view는 관계 정보가 있어야만 할 수 있는 기능에 집중한다. 값 검색 화면은 그대로 두되 아래 네 가지를 더한다.

갱신본 비교는 파일을 교체하거나 DB를 다시 불러올 때 이전 스냅샷과 새 스냅샷을 키 기준으로 비교한다. 테이블마다 추가, 삭제, 변경된 행 수를 보여주고, 변경된 행은 바뀐 열만 강조한다. 키는 관계에서 가리켜지는 열을 우선 쓰고, 없으면 값이 유일한 첫 열을 쓴다. 삭제되거나 키가 바뀐 행을 다른 테이블이 가리키고 있으면 "이 변경으로 깨지는 참조"로 따로 모은다. 비교하려면 이전 버전이 필요하므로, 교체 직전 파일은 OPFS에 한 벌 남겨 둔다.

참조 무결성 검사는 모든 관계를 한 번에 돌려 세 가지를 찾는다. 없는 ID를 가리키는 행(깨진 참조), 가리켜지는 열에 같은 값이 둘 이상 있는 경우(중복 키), 아무도 가리키지 않는 행(쓰이지 않는 데이터)이다. 관계마다 건수를 표로 보여주고, 누르면 해당 행 목록과 따라가기로 넘어간다.

사용처 추적은 행 하나를 고르면 그 행을 가리키는 곳을 관계 역방향으로 따라가 트리로 보여준다. 아이템 하나를 고르면 상점 상품, 보상, 드랍, 제작 재료, 퀘스트 조건 중 어디에서 쓰이는지, 그 보상은 다시 어느 퀘스트와 메일에서 쓰이는지를 단계별로 펼친다. 깊이는 기본 3단계이고 더 펼칠 수 있다.

행 참조 트리는 반대 방향이다. 퀘스트 하나를 고르면 보상 그룹, 보상, 아이템, 등급처럼 그 행이 가리키는 대상을 끝까지 펼친 트리를 한 화면에 보여준다. 4.4의 따라가기가 한 갈래씩 옆으로 이어 보는 방식이라면, 이쪽은 모든 갈래를 한꺼번에 펼쳐 보는 방식이다. 순환 참조(이전 퀘스트, 다음 대화 같은 자기 참조)는 이미 나온 행이면 더 펼치지 않는다.

### 4.10 50~300개 시트 다루기

시트가 많으면 화면마다 전체 목록을 늘어놓을 수 없다. 사이드바(6장)에서 시트 이름과 파일 이름으로 바로 걸러 찾게 하고, 관계 목록도 테이블로 거를 수 있게 한다. 다이어그램은 전체 보기 대신 고른 테이블에서 1~2단계 떨어진 테이블만 보여주는 초점 보기를 기본으로 하고, 전체 보기는 소스별로 묶어 접어 둔다.

적재는 지금처럼 앱을 열 때 모든 파일을 DuckDB에 올리는 방식으로 시작한다. 300개 시트에서 첫 화면까지 걸리는 시간을 실제 파일로 재 보고, 느리면 소스별로 처음 쓸 때 적재하는 방식으로 바꾼다. 자동 추천은 테이블 수의 제곱으로 비교가 늘어나므로, 진행률을 보여주고 소스나 테이블을 골라 범위를 좁혀 돌릴 수 있게 한다.

### 4.12 도메인 지도와 테이블별 연결

#### 문제

테이블 화면과 값 따라가기는 "이 테이블에서 저 테이블로"를 보여주지만, 앱은 회사 데이터의 도메인을 모른다. 그래서 51개 시트를 열어도 사용자에게 보이는 것은 시트 이름 목록과 표뿐이다. 실제로 막히는 지점은 다음과 같다.

- 처음 보는 데이터에서 어디서부터 봐야 하는지 모른다. 퀘스트나 상점 상품처럼 콘텐츠가 시작되는 테이블과, 아이템, 재화, 등급처럼 여러 곳에서 가져다 쓰는 테이블이 구분되지 않는다.
- 업무 단위(퀘스트, 보상, 아이템...)로 테이블이 어떻게 묶이고, 묶음끼리 어떻게 이어지는지 볼 곳이 없다.
- 전체 관계 다이어그램은 사용자가 저장한 관계만 그린다. 관계를 하나도 저장하지 않았으면 비어 있다. 자동 연결은 테이블 하나를 열 때 그 테이블 기준으로만 찾는다.
- 테이블마다 무엇과 이어지는지 보려면 테이블을 하나씩 열어야 한다.

값을 조회하는 것만으로는 쓸모가 적다. 데이터를 열자마자 도메인 구조가 보여야 한다.

#### 요구사항

| 번호 | 요구사항 |
| --- | --- |
| D1 | 열어 둔 모든 테이블의 자동 연결을 한 번에 찾고 저장한 관계와 합친다. 진행률을 보여주고, 결과는 데이터가 바뀌기 전까지 다시 계산하지 않는다. |
| D2 | 테이블을 도메인으로 묶는다. 파일은 파일 하나를 도메인 하나로 본다(Quest.xlsx → Quest). DB 테이블은 이름 접두어로 묶는다(QuestCondition → Quest). 하위 테이블만 따로 떨어지면 부모 도메인으로 보낸다. |
| D3 | 사용자가 테이블의 도메인을 바꿀 수 있다. 회사의 실제 업무 구분이 파일 구분과 다를 수 있어서다. 바꾼 값은 OPFS의 `domains.json`에 둔다. |
| D4 | 테이블마다 연결 구조로 역할을 붙인다(아래 표). 역할은 색과 글자를 같이 써서 색만으로 구분하지 않는다. |
| D5 | 도메인 지도: 도메인을 상자로, 도메인 사이 연결을 선으로 그린다. 선에는 연결 수를 적는다. 시작점이 많은 도메인은 왼쪽, 공통 도메인은 오른쪽에 둔다. |
| D6 | 도메인을 고르면 그 도메인 안의 테이블 연결 그림과, 바깥 도메인과의 연결(들어오는 쪽, 나가는 쪽)을 보여준다. 이 도메인을 설명하는 기획서 절도 붙인다. |
| D7 | 테이블별 연결: 모든 테이블을 도메인별로 묶어 카드로 보여주고, 카드마다 가리켜지는 테이블(왼쪽), 이 테이블, 가리키는 테이블(오른쪽)을 작은 그림으로 그린다. 이름과 열로 거를 수 있다. |
| D8 | 테이블 화면의 연결 그림에도 도메인과 역할을 표시한다. 테이블 제목 옆에 도메인과 역할, 역할 설명을 적는다. |

테이블 역할은 다음 순서로 정한다.

| 역할 | 조건 | 예 |
| --- | --- | --- |
| 하위 | 첫 열(키)이 다른 테이블의 키를 가리킨다. 그 테이블을 부모로 본다. | Equipment(→Item), Reward(→RewardGroup), CharacterLevel(→Character) |
| 공통 | 자기 도메인 밖의 3개 이상 도메인에서 가리킨다. | Item, Currency, Grade, RewardGroup |
| 기준 | 다른 테이블이 가리킨다. | QuestCondition, Npc, Buff |
| 시작점 | 아무도 가리키지 않고, 다른 테이블을 가리킨다. 기획 콘텐츠가 시작되는 곳이다. | Quest, ShopProduct, Stage |
| 독립 | 찾은 연결이 없다. | |

#### 화면

사이드바 메뉴의 맨 앞에 "도메인 지도"(`/map`)를 둔다. 탭은 "도메인 지도"와 "테이블별 연결"(`/map/tables`) 두 개다. 테이블 수가 많아도 도메인 지도는 도메인 수만큼만 상자를 그리므로 300개 시트에서도 읽을 수 있다. 테이블별 연결은 카드마다 React Flow를 띄우지 않고 SVG로 그린다.

역할 색은 범주형 색 1~4번(파랑, 주황, 청록, 노랑)을 시작점, 기준, 하위, 공통 순으로 고정해서 쓰고, 독립은 회색이다. 밝은 화면에서 청록과 노랑은 바탕과의 대비가 3:1보다 낮으므로 늘 역할 이름 글자와 같이 쓴다.

#### 구현

- `lib/client/domain-model.ts`: 테이블 목록, 관계, 첫 열, 사용자 지정 도메인을 받아 도메인, 역할, 도메인 사이 연결을 계산하는 순수 함수.
- `components/use-domain-model.ts`: 모든 테이블의 자동 연결(D1)을 진행률과 함께 구하고 위 모델을 만든다. 자동 연결은 테이블 화면과 같은 캐시(`findAutoLinks`)를 쓴다.
- `components/map/*`: 도메인 지도, 도메인 상세, 테이블별 연결 카드.

### 4.13 테이블 관계도

#### 문제

도메인 지도(4.12)는 전체를 위에서 내려다보는 화면이다. 실제로 일할 때는 사이드바에서 테이블 하나를 골라 "이 테이블이 무엇과 어떻게 이어지는지"부터 본다. 지금 사이드바에서 테이블을 누르면 데이터 화면이 열리고, 관계는 그 위의 작은 그림으로만 보인다. 막히는 점은 다음과 같다.

| 지금 | 문제 |
| --- | --- |
| 사이드바 테이블은 늘 데이터 화면으로 간다. | 관계를 보려고 눌러도 표가 화면 대부분을 차지한다. 도메인 지도에서 사이드바를 눌러도 데이터 화면으로 빠진다. |
| 연결 그림 상자에 테이블 이름만 있다. | 어느 열이 어느 열로 이어지는지는 선 이름표를 읽어야 안다. 한 테이블에서 같은 대상으로 가는 열이 여럿이면(`bonus_item_id_1~3`) 이름표가 겹친다. |
| 그림에서 이웃 테이블을 누르면 그 테이블의 데이터 화면으로 간다. | 관계를 따라 옮겨 다니며 구조를 익힐 수 없다. 매번 그림까지 다시 내려와야 한다. |
| 가리켜지는 테이블이 많으면(String 21개, RewardGroup 13개) 한 줄로 길게 늘어선다. | 그림이 세로로 길어지고 어느 도메인에서 오는지 안 보인다. |
| 그림은 테이블 화면을 열 때 그 테이블과 이웃만 따로 계산한다. | 이웃의 역할, 도메인, 2단계 연결을 도메인 지도와 다르게 볼 수 있다. |
| 사이드바의 관계 수는 저장한 관계만 센다. | 관계를 저장하지 않으면 자동으로 찾은 연결이 99개여도 0으로 보여, 어느 테이블이 연결의 중심인지 알 수 없다. |

#### 요구사항

| 번호 | 요구사항 |
| --- | --- |
| G1 | 테이블 화면을 "관계도"와 "데이터" 두 보기로 나눈다. 주소는 같은 테이블 경로에 `view=graph`(관계도) 또는 `view=data`(데이터)를 붙인다. 기획서의 "행 열기"(`row`)와 따라가기(`trail`)는 데이터 보기로 연다. |
| G2 | 사이드바에서 테이블을 누르면 마지막으로 쓴 보기로 연다. 처음에는 관계도다. 마지막 보기는 브라우저에 기억한다. 도메인 지도에 있을 때도 같은 동작이다. |
| G3 | 관계도는 가운데 테이블을 열 목록이 있는 상자로 그린다. 연결에 쓰이는 열과 키 열만 보여주고, 나머지 열은 "외 n개"로 접는다. 선은 열에서 열로 잇는다(`Quest.reward_group_id` → `RewardGroup.reward_group_id`). |
| G4 | 왼쪽은 이 테이블을 가리키는 테이블, 오른쪽은 이 테이블이 가리키는 테이블이다. 이웃 상자에는 연결에 쓰인 열, 역할 색, 다른 도메인이면 도메인 이름을 적는다. 이웃은 도메인끼리 모아 둔다. |
| G5 | 한쪽 이웃이 12개를 넘으면 도메인별 묶음 상자("Event 도메인 3개")로 접고, 누르면 펼친다. |
| G6 | 깊이 1~2단계를 고른다. 2단계는 이웃의 이웃을 바깥 열에 두고, 이미 나온 테이블은 다시 그리지 않는다. |
| G7 | 이웃 테이블을 누르면 그 테이블이 가운데로 오고 관계도 보기를 유지한다. 주소가 바뀌어 뒤로 가기로 이전 테이블로 돌아간다. 위쪽에 지나온 테이블 경로를 보여준다. 이웃 상자의 "데이터" 단추로 그 테이블의 데이터 보기를 연다. |
| G8 | 선에 마우스를 올리면 연결 근거(저장한 관계인지, 자동 연결이면 이름 규칙과 일치율)를 보여준다. 자동 연결은 지금처럼 점선이고, 선 옆 단추로 관계로 저장한다. |
| G9 | 관계도 오른쪽에 정보 칸을 둔다. 도메인과 역할, 부모, 행 수, 가리키는/가리켜지는 테이블 수, 기획서 설명(4.11의 TableDocNotes), 기획서에 나온 ID, 도메인 지도에서 이 도메인 보기 링크를 둔다. |
| G10 | 사이드바 테이블 줄의 관계 수는 저장한 관계와 자동 연결을 합친 수로 바꾸고, 앞에 역할 색 점을 둔다. 도메인 모델(4.12)을 아직 계산하지 못했으면 지금처럼 저장한 관계 수를 보여준다. |
| G11 | 데이터 보기는 지금 화면을 그대로 쓴다. 위쪽의 작은 연결 그림은 두되 기본으로 접고, "관계도로 보기" 링크를 둔다. |

#### 설계

화면 배치는 다음과 같다.

```
┌ Quest  [관계도] [데이터]                         Quest 도메인 · 시작점 ┐
│ 지나온 길: Item > RewardGroup > Quest                     깊이 [1][2]  │
├──────────────────────────────────────────────────────────┬───────────┤
│  가리켜지는 쪽            가운데                 가리키는 쪽 │ 정보 칸    │
│ ┌Achievement┐        ┌ Quest ─────────┐    ┌QuestCondition┐│ 역할, 부모 │
│ │condition_id├─────▶ │ quest_id (키)  │    │condition_id  ││ 행 수      │
│ └───────────┘        │ condition_id   ├──▶ └──────────────┘│ 기획서     │
│ ┌Event 도메인 3개┐   │ npc_id         ├──▶ ┌Npc · Npc┐     │ 기획서 ID  │
│ └───────────────┘    │ reward_group_id├──▶ ┌Reward · RewardGroup┐       │
│                      │ 외 3개         │                     │           │
│                      └────────────────┘                     │           │
└──────────────────────────────────────────────────────────┴───────────┘
```

- 데이터: 도메인 모델(`useDomainModel`)의 `TableInfo.in/out`을 그대로 쓴다. 모든 테이블의 연결을 이미 구해 두므로 2단계도 추가 조회 없이 그린다. 모델을 계산하는 중이면 지금처럼 그 테이블만의 자동 연결(`useLinkedRelations`)로 1단계를 먼저 그리고, 진행률을 작게 보여준다.
- 열 목록: 가운데 상자의 열은 `loadColumns()`에서 읽고, 연결에 쓰인 열을 위에, 키 열을 맨 위에 둔다. 이웃 상자는 연결에 쓰인 열만 적는다.
- 선: React Flow의 열 단위 연결점(handle)으로 잇는다. 관계 다이어그램의 `TableNodeView`가 이미 열마다 연결점을 두므로, 같은 방식으로 관계도용 노드를 만든다. 같은 두 상자 사이의 선이 여럿이면 열마다 따로 그려 이름표가 겹치지 않게 한다.
- 배치: 열(column)마다 도메인별로 모으고, 같은 도메인 안에서는 역할 순서(시작점, 기준, 하위, 공통)와 이름 순서로 놓는다. 상자 높이는 열 줄 수로 계산해 겹치지 않게 쌓는다.
- 주소: `/sources/[id]/tables/[table]?view=graph&depth=2`. 기본 보기는 `view`가 없을 때 브라우저에 기억한 마지막 보기를 쓴다. 가운데 테이블을 바꿀 때는 Next 라우터로 이동한다(테이블 경로가 바뀌므로). 지나온 길은 `history.state`에 둔다.
- 사이드바: 링크 주소는 그대로 테이블 경로로 두고, 테이블 화면이 `view`가 없을 때 마지막 보기를 고른다. 사이드바와 화면이 같은 규칙을 한 곳(`lib/client/table-view.ts`)에서 읽는다.
- 재사용: 역할 색과 배지(`components/map/map-parts.tsx`), 기획서 설명(`TableDocNotes`), 자동 연결 저장(`RelationChip`의 저장 동작)을 그대로 쓴다. 도메인 지도와 테이블별 연결 화면은 바꾸지 않는다. 테이블 카드의 테이블 이름 링크만 관계도 보기로 연다.

#### 정한 것

- 처음 보기는 관계도이고, 마지막으로 고른 보기를 기억한다.
- 관계도에는 가운데 테이블의 실제 행을 넣지 않는다. 값까지 보이면 화면이 다시 표 쪽으로 무거워지므로 "데이터" 보기로 넘긴다.

#### 구현

- `lib/client/table-view.ts`: 보기 기억(localStorage), `view`, `depth`, `via` 쿼리 읽기와 주소 만들기.
- `lib/client/relation-layout.ts`: 관계도 배치(순수 함수). 열 단위 연결점 id는 `in:<열>`, `out:<열>`, 상자 머리는 `in`, `out`이다.
- `components/relation-view/table-relation-view.tsx`: 관계도 화면. 상자, 선 근거 말풍선, 선을 눌러 관계로 저장, 지나온 길, 깊이, 정보 칸.
- `components/table-page.tsx`: 관계도/데이터 탭과 보기 고르기. 데이터 보기는 `TablePreview` 그대로다.

### 4.11 기획서 연동

기획서는 워드(docx), PPT(pptx), PDF, 엑셀 파일로 받는다. 데이터 파일처럼 소스 추가 메뉴로 열고, 원본은 OPFS에 두며, 사이드바에 "기획서" 묶음으로 보인다. 같은 기획서의 새 판을 받으면 데이터 파일처럼 교체하고, 이전 판에서 확정해 둔 이름 매칭은 그대로 이어 쓴다.

읽기는 모두 브라우저 안에서 한다. docx와 pptx는 압축 안의 XML에서 문단, 표, 슬라이드 텍스트를 꺼내고, PDF는 pdf.js로 쪽마다 텍스트를 꺼내고, 엑셀은 지금처럼 SheetJS로 읽는다. 꺼낸 내용은 "절" 단위로 나눈다. 워드는 제목 문단, PPT는 슬라이드, PDF는 쪽, 엑셀은 시트를 한 절로 본다. 문서 안의 표는 머리글과 행을 살려 따로 들고 있는다. 불일치 검출이 이 표를 쓴다.

이름 매칭(추론)은 기획서에서 테이블, 열, ID로 보이는 말을 뽑아 실제 데이터와 잇는 일이다. 뽑는 대상은 영문 식별자(`QuestReward`, `reward_group_id`, `ITEM`), "~ 테이블"이나 "Table:" 같은 표현 앞의 말, 문서 표의 머리글, 키 범위에 들어가는 숫자(예: 100523)다. 각 말에 대해 후보 테이블과 열을 점수와 근거를 붙여 보여준다. 점수는 아래 규칙을 합쳐 낸다.

| 규칙 | 예 |
| --- | --- |
| 이름 정규화 후 일치 | `QuestRewardTable`, `quest_reward` → 접두어/접미어(Table, Data, Info, List, 테이블, 정보)와 구분자를 떼고 비교 |
| 단어 단위 겹침 | `QuestReward`와 `Reward`는 Reward가 겹친다 |
| 편집 거리 | 오타나 옛 이름(`Reword`) |
| 용어집 | 아이템=Item, 보상=Reward처럼 사용자가 고칠 수 있는 한영 대응표 |
| 다국어 문자열 테이블 | 기획서의 "전설의 검"을 String 테이블의 ko에서 찾아 key, 그 key를 쓰는 Item 행으로 잇는다 |
| 값 일치 | 기획서에 나온 ID 100523이 Item.item_id에만 있으면 그 숫자는 아이템 ID로 본다 |

추론 결과는 사용자가 확정해야 매칭으로 저장된다(`doc-mappings.json`). 끝까지 맞는 테이블이 없는 말은 "기획서에만 있음"(옛 이름이거나 아직 안 만든 테이블), 어느 기획서에도 나오지 않는 테이블은 "기획서에 없음"으로 따로 모은다. 둘 다 기획서가 최신이 아니라는 신호라 테스트할 때 먼저 볼 곳이 된다.

불일치 검출은 기획서의 표와 "보상 골드: 500" 같은 "이름: 값" 문장을 실제 데이터와 맞춰 본다. 문서 표의 머리글이 어떤 테이블의 열로 매칭되어 있고 키 열(ID)이 있으면, 키로 행을 찾아 칸마다 값을 비교한다. 결과는 "기획서 값, 데이터 값, 위치(문서 절과 테이블 행)" 목록으로 보여주고, 숫자는 표기 차이(1,000과 1000, 10%와 0.1)를 맞춘 뒤 비교한다.

기획서 화면은 절 목록, 본문, 용어 패널을 한 화면에 둔다. 본문과 용어 매칭을 탭으로 나누면 오가며 보기 불편해서다. 본문에서 용어를 누르면 오른쪽 패널에 후보가 펼쳐지고 그 자리에서 확정한다. 숫자 ID는 문서 표의 어느 칸(예: quest_id)에 나왔는지도 근거로 쓴다. 키 범위가 겹치는 테이블(Quest와 QuestCondition)을 가르기 위해서다. 여러 테이블에 있는 열 이름은 그 열이 키인 테이블을 대표로 본다. "기획서에만 있음"은 같은 이름의 테이블이나 열이 없고 확실한 후보(85% 이상)도 없는 이름으로 정한다.

양방향 이동은 두 방향이다. 기획서 화면에서는 매칭된 말과 ID에 링크를 걸어 눌렀을 때 테이블 행과 따라가기 패널(4.4)을 연다. 테이블 화면에서는 "관련 기획서" 칸에 이 테이블과 이 행의 ID가 나오는 절을 보여준다.

테스트 항목은 기획서 절 하나를 기준으로 만든다. 절에 매칭된 테이블과 ID를 행 참조 트리(4.9)로 펼쳐 "퀘스트 71005 완료 보상: 보상 그룹 50012, 아이템 101699 9개" 같은 확인 항목을 만들고, 불일치나 깨진 참조가 걸린 항목은 위로 올린다. 항목마다 확인, 문제, 보류를 표시하고 메모를 남길 수 있으며, 엑셀로 내보낸다. 진행 상태는 OPFS의 `checklists.json`에 둔다.

## 5. 시각화

차트 라이브러리는 ECharts 하나로 간다. 막대, 선, 파이, 산점도를 모두 지원하고, 수천 개 점의 산점도도 캔버스로 무리 없이 그린다. 표는 TanStack Table에 가상 스크롤(TanStack Virtual)을 붙인다.

차트 빌더는 테이블을 고른 뒤 차트 종류, X축 컬럼, Y축 컬럼과 집계 함수(count, sum, avg, min, max), 그룹 컬럼, 필터를 고르는 방식이다. 빌더 설정은 아래 형태로 저장하고, 실행할 때 소스에 맞는 SQL로 바꾼다. MySQL이면 서버로, 파일과 Qdrant payload면 DuckDB로 보낸다. 직접 SQL을 쓰는 모드도 둔다.

```ts
interface ChartSpec {
  sourceId: string;
  table: string;
  chartType: 'bar' | 'line' | 'pie' | 'scatter' | 'table';
  x?: string;
  y?: { column: string; agg: 'count' | 'sum' | 'avg' | 'min' | 'max' }[];
  groupBy?: string;
  filters?: { column: string; op: '=' | '!=' | '>' | '<' | 'in' | 'like'; value: unknown }[];
  sql?: string; // 직접 SQL 모드
}
```

대시보드는 저장한 차트를 격자에 배치한 화면이다. 배치는 react-grid-layout으로 하고 위치와 크기만 저장한다.

## 6. 화면 구성

### 6.1 레이아웃

왼쪽에 사이드바, 오른쪽에 본문을 두는 2단 구성이다. 상단 가로 메뉴는 없앤다.

본문 위에는 상단 바를 둔다. 왼쪽은 현재 위치 경로, 오른쪽은 파일/테이블/관계 수, 값 검색 입력칸, 소스 추가 메뉴(데이터 테이블과 기획서를 각각 "파일 선택" 또는 "경로 지정"으로 불러오기, 데이터베이스 연결, 벡터 DB 연결. 경로 지정은 `/sources/new/path?kind=data|doc`으로 열고, 종류에 따라 xlsx를 데이터나 기획서로 기본 지정하며 최근 경로를 종류별로 기억한다), 화면 테마 전환(시스템, 밝게, 어둡게)이다. 테마는 브라우저에 기억하고, 첫 화면이 깜빡이지 않도록 HTML이 그려지기 전에 테마 클래스를 붙인다.

사이드바 위쪽에는 메뉴(데이터 소스, 관계, 값 검색, 합친 표)를 두고, 그 아래에 열어 둔 모든 테이블을 소스 종류별로 묶은 트리를 둔다. 묶음은 파일, 데이터베이스, 벡터 DB 순서이고, 소스가 하나도 없는 묶음은 숨긴다. 소스를 펼치면 시트(테이블, 컬렉션) 목록이 나오고, 시트마다 행 수와 걸린 관계 수를 작게 붙인다. 트리 위의 입력칸으로 시트 이름과 파일 이름을 걸러 찾는다. 걸러진 시트가 있는 소스는 자동으로 펼친다. 지금 보고 있는 시트는 강조하고, 사이드바는 접을 수 있으며 접힘 상태는 브라우저에 기억한다.

본문은 너비 제한 없이 화면을 다 쓴다. 정보 밀도를 높이려고 본문 글자는 13px 안팎, 표 행 높이는 28px 안팎으로 두고, 여백은 지금보다 줄인다. 색은 지금처럼 회색 단색을 기본으로 하고, 관계 링크(파랑), 누락과 경고(주황), 오류(빨강)에만 색을 쓴다.

### 6.2 테이블 화면

표만 보여주면 GDF와 다를 게 없으므로, 테이블을 열면 표 위에 세 가지를 먼저 보여준다(7단계에서 구현).

- 이어진 테이블 그림: 지금 테이블을 가운데, 이 테이블을 가리키는 테이블을 왼쪽, 이 테이블이 가리키는 테이블을 오른쪽에 둔다. 깊이는 1~2단계를 고르고, 선 이름표에 어떤 열로 이어지는지 적고, 상자를 누르면 그 테이블로 간다. 저장한 관계와 자동 연결(4.8.1)을 같이 그린다.
- 기획서 설명: 그림 바로 아래에 이 테이블을 설명하는 기획서 절과 문장을 보여준다. 이 테이블로 확정한 용어, 이름이 같은 말(QuestTable), 용어집으로 바꾸면 같은 말(퀘스트 테이블)이 나오는 절을 찾고, 누르면 기획서의 그 절로 간다.
- 표 안 검색: 모든 열 또는 고른 열에서 일부만 맞아도 찾는다.

열 정보 줄은 데이터 표의 머리글에 둔다(20단계). 열 이름 아래에 열 종류, ID 열 여부(값이 모두 다르고 빈 칸이 없음, 98% 기준. 같은 값이 섞였으면 "중복 n"), 빈 칸 비율(엑셀에서 지운 빈 글자도 빈 칸으로 셈), 값 종류 수, 이 열이 쓰는 테이블(→), 이 열을 쓰는 곳(← n곳)을 적는다. 머리글에 마우스를 올리면 채워진 칸 수, 범위(숫자면 최솟값~최댓값), 자주 나오는 값 5개, 연결 목록을 보여준다. 범위에 깨진 ID(9000000대)가 바로 드러나는 식으로 QA가 이상한 열을 먼저 알아보게 하려는 목적이다. 셈은 테이블마다 쿼리 한 번이고, 자주 나오는 값과 범위는 마우스를 올렸을 때만 구한다. 오른쪽에는 지금처럼 따라가기 패널이 붙는다.

### 6.4 값에 마우스를 올리면 보이는 설명

표의 값은 원본 그대로 둔다(`100041`, `ITEM_100041`, `5`). QA는 값을 고치지 않고 확인하는 사람이라, 화면의 값이 파일과 다르면 오히려 헷갈린다. 대신 값에 마우스를 0.3초 올리면 앱이 그 값이 어떤 데이터인지 추론해 말풍선으로 보여준다.

| 칸 | 보여주는 것 |
| --- | --- |
| 다른 테이블을 쓰는 열(`reward_group_id`) | 그 테이블의 행. 이름, 주요 값, 세부 행(보상 그룹이면 보상 3개), 그 ID를 쓰는 곳 |
| 행 자신의 ID 열(첫 열) | 이 행의 이름과 주요 값, 이 행을 쓰는 곳 |
| 다국어 글을 쓰는 열(`name_key`) | 그 글(ko)과 다른 언어 |
| 상대 테이블에 없는 값 | "Item에 100092이(가) 없습니다"와 없는 ID 찾기 안내 |

이름은 그 행에서 다국어 글 테이블을 쓰는 열(`name_key`)의 글을 쓰고, 없으면 `name`, `이름` 같은 열, 그것도 없으면 `memo`, `설명` 같은 메모 열을 쓴다. 주요 값 가운데 다른 테이블을 쓰는 값은 한 단계만 더 풀어 이름을 붙인다(`grade_id 1 · 일반`). 세부 행의 `reward_type ITEM` + `reward_id 101821` 같은 타입+ID는 타입 값과 이름이 같은 테이블에서 이름을 찾는다(16단계 전의 임시 규칙). 테이블 이름은 기획서 이름 짝(아이템=Item)을 거꾸로 써서 한글 이름을 붙인다.

데이터 화면의 표, 따라가기 패널, ID·값 찾기 결과에 적용한다. 말풍선은 화면에 하나만 두고(`ExplainLayer`), 같은 값의 설명은 기억해 두었다가 다시 쓴다.

## 7. 서버 API

Route Handler는 Node 런타임에서 돈다. 이 프로젝트는 Next.js 16의 Cache Components가 켜져 있어서 `runtime` route segment config를 쓸 수 없고, 기본값이 Node 런타임이다.

| 메서드, 경로 | 설명 |
| --- | --- |
| `GET/POST /api/sources` | 소스 목록, 추가 |
| `PATCH/DELETE /api/sources/[id]` | 수정, 삭제 |
| `POST /api/sources/[id]/test` | 접속 테스트 |
| `GET /api/mysql/[id]/schema` | 테이블과 컬럼 목록 |
| `POST /api/mysql/[id]/query` | SQL 실행, QueryResult 반환 |
| `GET /api/qdrant/[id]/collections` | 컬렉션 목록과 요약 |
| `GET /api/qdrant/[id]/collections/[name]` | 컬렉션 상세 통계 |
| `POST /api/qdrant/[id]/collections/[name]/scroll` | payload, 벡터 샘플 |
| `POST /api/qdrant/[id]/collections/[name]/query` | 유사도 검색 |
| `GET/POST /api/charts`, `GET/POST /api/dashboards` | 저장한 차트, 대시보드 |

에러 응답은 `{ error: { code, message } }`로 통일한다. 화면에는 code를 보고 사용자 문구로 바꿔서 보여주고, DB 원문 에러는 상세 보기에서만 보여준다.

## 8. 앱 저장소

연결 정보와 차트, 대시보드는 프로젝트 안 `data/app.db`(SQLite, better-sqlite3)에 둔다. `data/`는 git에서 제외한다. 테이블은 세 개로 시작한다.

```sql
CREATE TABLE sources (
  id TEXT PRIMARY KEY,
  type TEXT NOT NULL,          -- 'mysql' | 'qdrant' | 'file'
  name TEXT NOT NULL,
  config TEXT NOT NULL,        -- JSON. 비밀값은 암호화해서 저장
  created_at TEXT NOT NULL
);

CREATE TABLE charts (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  spec TEXT NOT NULL,          -- ChartSpec JSON
  updated_at TEXT NOT NULL
);

CREATE TABLE dashboards (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  layout TEXT NOT NULL,        -- [{ chartId, x, y, w, h }]
  updated_at TEXT NOT NULL
);
```

파일 소스와 관계는 app.db가 아니라 브라우저 OPFS에 둔다(`sources.json`, `relations.json`, `files/<소스 id>/`). 파일 원본이 브라우저에만 있으므로 관련 정보도 같은 곳에 두는 편이 어긋날 일이 적다. 대신 다른 브라우저에서는 보이지 않으므로, 옮기거나 나눌 때는 관계 내보내기를 쓴다. app.db는 MySQL, Qdrant 연결 정보와 차트, 대시보드만 담는다.

MySQL 비밀번호와 Qdrant API 키는 `.env.local`의 `APP_SECRET`으로 AES-GCM 암호화해서 `config`에 넣는다. 로컬 도구라도 `app.db`를 실수로 공유하거나 백업할 때 평문이 새는 것을 막기 위해서다. 화면에는 비밀값을 다시 내려보내지 않고, 수정할 때만 새로 입력받는다.

## 11. 단계별 계획

체이닝 문제를 먼저 풀도록 관계 기능을 차트와 DB 연결보다 앞에 둔다.

1단계는 프로젝트 기반과 파일 소스다. Next.js 세팅, DuckDB-WASM 초기화, CSV와 엑셀 열기, 데이터 미리보기 표까지 만든다. (완료)

2단계는 관계 정의다. 엑셀 테이블 이름을 시트 이름 기준으로 바꾸고, 파일 교체, 관계 수동 생성과 검증 수치, 자동 추천, 내보내기/가져오기를 만든다. (완료)

3단계는 값 클릭 따라가기와 값 검색이다. 체이닝을 실제로 대체하는 기능이라 관계 정의 바로 다음에 둔다. (완료)

4단계는 관계 다이어그램이다. (완료)

5단계는 합친 표와 엑셀 내보내기다. (완료)

5단계까지 마친 뒤 기준 데이터를 게임 테이블 수준으로 올렸다. 그래서 차트와 DB 연결보다 복잡한 테이블을 다루는 기능을 먼저 한다.

6단계는 사이드바 레이아웃이다. 상단 메뉴를 사이드바로 옮기고, 소스 종류별 테이블 트리, 시트 이름 거르기, 행 수와 관계 수 표시, 접기를 만든다. 본문 여백과 글자 크기도 정보 밀도 기준으로 줄인다. (완료. 행 수는 테이블마다 count를 돌리지 않고 `duckdb_tables()`의 `estimated_size`로 한 번에 읽는다.)

7단계는 게임 테스트 데이터, 다크 모드, 소스 추가 메뉴, MySQL 스냅샷 연결이다(3.2). 테스트 데이터는 생성 스크립트로 만들고, 같은 데이터를 MySQL 테스트 컨테이너에도 넣는다. (완료. 실제 MySQL 접속은 테스트 컨테이너를 띄운 뒤 확인한다.)

GDF와 다른 쓸모가 기획서 연동에 있으므로, 그다음은 기획서를 먼저 한다.

8단계는 기획서 불러오기와 이름 매칭이다(4.11). 워드, PPT, PDF, 엑셀 기획서를 열어 절과 표로 나누고, 테이블, 열, ID 후보를 뽑아 규칙 기반으로 추론하고 확정한다. 용어집과 다국어 문자열 테이블을 쓰는 추론도 여기서 만든다. 테스트용으로 데이터와 일부러 어긋난 옛 기획서(없는 테이블 이름, 바뀐 수치)를 생성 스크립트에 더한다. (완료. 같은 단계에서 경로 불러오기, 환경변수 DB 연결, 테이블 화면의 연결 그림, 기획서 설명, 표 안 검색, 테이블별 자동 연결(4.8.1)도 만들었다.)

9단계는 기획서와 데이터 사이의 양방향 이동이다(4.11). (완료. 기획서에서 확정한 ID와 따옴표 이름, 용어 패널의 후보마다 "행 열기"를 붙였다. 누르면 테이블 화면이 `row` 쿼리로 그 행만 걸러 보여주고, 그 키 열을 가리키는 테이블이 있으면 따라가기 패널을 바로 연다. 테이블 화면에는 "이 행이 나오는 기획서"와 "기획서에 나온 ID"(기획서의 숫자 중 이 테이블 키에 있는 값)를 더했다.)

10단계는 도메인 지도와 테이블별 연결이다(4.12). 앱이 회사 데이터의 도메인을 모른 채 표만 보여준다는 문제를 풀기 위해 참조 방식 확장보다 앞에 둔다. (완료. 게임 테스트 데이터에서 도메인 15개, 연결 99개를 찾았고, 51개 테이블의 연결을 모두 찾는 데 약 6.5초 걸렸다. 같은 단계에서 자동 연결이 쓰임새가 붙은 키 열과 행 기준 일치율을 보도록 넓혔다(4.8.1). 넓히기 전에는 연결 34개, 독립 테이블 15개였다.)

11단계는 테이블 관계도다(4.13). 사이드바에서 테이블을 누르면 그 테이블의 관계도를 먼저 보여준다. 도메인 지도가 전체를 내려다보는 화면이라면, 이쪽은 테이블 하나에서 출발해 관계를 따라 옮겨 다니는 화면이다. (완료. 처음 보기는 관계도로 하고 마지막 보기를 기억한다. 관계도에 실제 행은 넣지 않았다. 모든 연결을 찾기 전에는 그 테이블만의 자동 연결로 1단계를 먼저 그리고, 역할과 2단계는 다 찾은 뒤에 보여준다.)

12단계는 QA 엔지니어에 맞춘 말과 첫 화면이다(1.1). 화면의 공학 용어를 용어 대응표대로 바꾸고, 연결 근거를 비율 대신 개수로 보여주고, DB 접속과 연결 내보내기 같은 설정을 "고급"으로 옮기고, 첫 화면을 질문 입구로 바꾼다. 기능을 더 만들기 전에 지금 있는 기능을 사용자가 알아볼 수 있게 하는 일이라 가장 먼저 한다. (완료. 첫 화면은 `/`의 질문 입구, 불러온 파일 목록은 `/files`로 옮겼다. 연결 근거는 "1,500행 중 1,495행 맞음, 5행은 상대 테이블에 없는 ID"처럼 쓴다. 개발 DB 연결은 파일 불러오기 메뉴의 "고급", 환경변수/.env 불러오기와 연결 내보내기/가져오기는 각 화면의 접힌 "고급"으로 옮겼다. 기획서 화면의 추정 점수(%)는 화면에서 뺐고 정렬에만 쓴다.)

13단계는 기획서와 데이터의 불일치 검출이다(4.11). QA가 바로 쓰는 기능이라 15~17단계였던 불일치 검출, 갱신본 비교, 참조 무결성 검사를 참조 방식 확장보다 앞으로 당겼다. (완료. 기획서 표 중 머리글에 테이블의 ID 열이 있는 표를 골라 그 ID의 행과 칸마다 비교한다. 결과는 기획서 화면 위의 "데이터와 맞춰 본 결과"와 본문 표의 칸 색으로 보여주고, 기획서 목록에 기획서마다 다른 곳 수를 붙였다. 테스트 기획서 3종에서 의도한 어긋남 9개(다른 값 7, 없는 ID 2)를 모두 찾았고 잘못 잡은 것은 없었다. "보상 골드: 500" 같은 문장 속 수치 비교는 남았다.)

14단계는 갱신본 비교(화면 이름 "패치 전후 비교")다(4.9). (완료. `/compare`. 파일을 교체하면 바로 전 파일을 OPFS `files/<소스 id>/prev/`에 한 벌 남기고, 비교할 때 `p_<소스 id>` 스키마에 올려 시트마다 ID 열 기준으로 새로 생긴 행, 사라진 행, 값이 바뀐 행, 열 변화를 센다. 시트를 고르면 바뀐 값(전→후), 새로 생긴/사라진 ID, 사라진 ID를 아직 쓰는 곳("이 변경으로 깨지는 곳")을 보여준다. 테스트 데이터 Item 이전 버전→지금 버전: 새로 생긴 40, 사라진 25, 바뀐 60, 깨지는 곳 11곳. 개발 DB 비교와, 시트 안에서 ID 자체가 바뀐 경우를 따로 잡는 일은 남았다.)

15단계는 참조 무결성 검사(화면 이름 "없는 ID 찾기")다(4.9). (완료. `/check/missing`. 모든 연결(확인한 연결과 앱이 찾은 연결)을 하나씩 돌려 다른 테이블에 없는 ID를 쓰는 행과 ID 열의 중복 ID를 모은다. 줄을 펼치면 없는 ID 목록이 나오고, ID를 누르면 그 ID를 쓰는 행을 데이터 화면에서 연다. 연결 그림의 선 설명에서 "없는 ID 보기"로 바로 간다. 테스트 데이터에서 연결 99개 중 59곳(436행)과 중복 ID 1곳을 찾았다. 아무도 쓰지 않는 행 찾기는 남았다.)

16단계는 참조 방식 확장이다(4.8). 관계 모델을 `columns`, `separator`, `when`으로 넓히고, 일치율, 따라가기, 값 검색, 합친 표, 다이어그램을 펼친 값 기준으로 바꾼다. 기존 관계 파일은 읽을 때 바꾼다. (완료. 관계의 쓰는 쪽에 `columns`, `separator`, `when`을 더했고, 예전 관계와 맞추려고 `column`은 대표 열(첫 열)로 남겼다. 일치 확인, 따라가기, 없는 ID 찾기, 값 설명, 연결 그림, 시스템 지도가 펼친 값으로 동작한다. 표에서 한 칸 여러 ID는 ID마다 따로 링크와 설명을 달고, 타입+ID 열은 행의 종류 값에 맞는 연결이 있을 때만 링크와 설명을 단다. 직접 잇기에서 네 가지 방식을 고른다. 여러 테이블 붙여 보기는 한 행이 여러 행으로 늘어나는 처리가 필요해 아직 단일 열 연결만 쓴다. 자동으로 찾는 일은 17단계다.)

17단계는 확장된 자동 추천이다. 번호 붙은 열 묶음, 구분자, 타입+ID 후보를 찾는다. (완료. 테이블마다 자동 연결을 찾을 때 세 가지를 더 본다. 끝 번호만 다른 ID 열 묶음(material_id_1~5, 수량 열은 뺌), 표본 300행에서 구분 글자(| ; , /)가 자주 나오고 나눈 조각이 거의 숫자인 열, 접두어가 같은 종류 열과 ID 열(reward_type, reward_id)의 종류 값마다 같은 이름의 테이블. 이름으로 대상을 못 찾으면 값으로 찾고, 이때는 고유값 기준으로도 90% 이상 맞아야 한다. 대상이 여럿이면(effect_ids → ItemEffect, SkillEffect) 가장 잘 맞는 하나만 남긴다. 게임 테스트 데이터에서 연결이 99개에서 117개로 늘었고, 모든 테이블을 찾는 데 8.3초 걸렸다. QuestCondition의 cond_type과 target_id처럼 접두어가 다른 종류+ID는 아직 찾지 못한다.)

18단계는 사용처 추적과 행 참조 트리다(4.9). 둘 다 관계를 따라 트리를 펼치는 같은 바탕을 쓴다. (완료. 데이터 표의 행 번호를 누르면 오른쪽에 "이 행이 쓰는 것"(행 참조 트리)과 "이 행을 쓰는 곳"(사용처 추적) 트리가 열린다. 처음에는 두 단계까지 펼치고, 그다음은 노드를 누를 때마다 한 단계씩 구한다. 쓰는 것 쪽은 세부 테이블(보상 그룹 → 보상)의 행도 펼치고, 이름 글(String)은 노드 이름에 들어가므로 따로 펼치지 않는다. 쓰는 곳 쪽은 세부 행(보상, 드랍 아이템)이 쓰면 그 위 행(보상 그룹, 드랍 그룹)으로 올려서 다음 단계(퀘스트, 몬스터)로 이어 간다. 이미 나온 행은 다시 펼치지 않는다. 한 갈래에 20행까지 보여준다. 설계의 "깊이 기본 3단계"는 노드마다 펼치는 방식으로 바꿨다.)

19단계는 기획서 기준 테스트 항목이다(4.11). 행 참조 트리를 바탕으로 만든다. (완료. 기획서 화면의 "테스트 항목 만들기"나 절 제목 옆 "이 절로 테스트 항목"으로 `/docs/[id]/checklist`를 연다. 절에 나온 ID 가운데 "맞음"으로 표시했거나 확실한 추정(85% 이상)인 것과, 불일치 검출에서 데이터에 없다고 나온 ID로 항목을 만든다. 항목마다 행 트리의 "이 행이 쓰는 것"을 3단계까지 펼쳐 확인 내용을 적고(세부 행에서 위 행으로 되돌아가는 줄은 뺀다), 기획서와 다른 값, 데이터에 없는 ID, 없는 ID를 쓰는 줄이 있는 항목을 위로 올린다. 확인, 문제, 보류와 메모는 OPFS `checklists.json`에 기획서와 항목(테이블 키|ID)별로 남고, 절 단위로 엑셀로 내보낸다. 테스트 기획서의 "메인 퀘스트 보상표" 절에서 항목 18개, 먼저 볼 항목 3개(71005, 71038 보상 그룹 다름, 79999 데이터에 없음)가 나왔다.)

20단계는 테이블 열 정보 줄이다(6.2). (완료. 6.2 참고.)

21~30단계는 회사 도구의 기능을 옮기고 회사에서 실행할 수 있게 보안을 고치는 일이다. 단계별 내용과 지금 코드와 맞춰 본 결과는 [PLAN.md](PLAN.md)에 있다. 보안 고치기(21, 완료), 가짜 데이터 늘리기(22), 엑셀 읽기 규칙(23), 컬럼 설명과 연결 근거(24), 한글 이름(25), 기획서 원문과 관련 기획서(26), 값 찾기 색인과 행 출처 전환(27), 용어 통일(28), QA 우선 높음(29), QA 우선 중간(30) 순서다.

31단계는 시트가 많을 때의 대응이다(4.10). 다이어그램 초점 보기, 관계 목록 거르기, 추천 범위 지정과 진행률을 한다. 적재 시간은 게임 테스트 데이터(15개 파일, 51개 시트, 약 5만 9천 행)로 새로고침 후 복원까지 2.3초였고, 300개 시트에서 다시 잰다. (완료. 참조 관계 그림에 「초점 보기」(고른 테이블에서 1~2단계, 시트가 30개보다 많으면 기본)와 「전체 보기」(시트가 많으면 파일별로 접고 고른 파일만)를 두었다. 행 수는 테이블마다 count를 돌리지 않고 메타데이터로 한 번에 읽는다. 참조 관계 목록에 테이블·컬럼·파일 이름 거르기, 추천에 찾을 범위(파일 고르기)와 진행률(테이블 읽는 중, 비교하는 중)을 더했다. 추천은 숫자 범위가 겹치지 않거나 한쪽만 숫자인 짝을 값을 세기 전에 건너뛰어, 게임 데이터 추천 결과(확실 30, 낮음 111)는 그대로이고 시간은 58.9초에서 17.6초로 줄었다. 가짜 300시트(`npm run fixtures:many`, 20개 파일, 4만 5천 행)로 잰 시간: 처음 불러오기 5.4초, 새로고침 후 복원 6.9초, 모든 테이블의 자동 참조 관계 찾기 약 42~46초, 파일 2개(30시트) 범위 추천 6.8초. 복원이 7초 안쪽이라 처음 쓸 때 적재하는 방식으로는 바꾸지 않았다. 자동 참조 관계 찾기는 진행률을 보여주며 뒤에서 돌고, 그동안 다른 쿼리는 차례를 기다린다.)

32단계는 차트 빌더와 DB 실시간 조회다.

33단계는 Qdrant다. 컬렉션 통계, payload 메타데이터(DuckDB 경로 재사용), 산점도, 유사도 검색 순서로 진행하고 사이드바의 벡터 DB 묶음에 넣는다.

34단계는 차트 저장과 대시보드다.

## 12. 정하지 않은 것

기획서 이름 추론은 규칙 기반으로 시작한다. 실제 사내 기획서로 맞히는 비율을 재 보고, 부족하면 PC 안에서 도는 로컬 모델을 붙일지 다시 정한다. 기획서 문장에서 수치를 뽑는 규칙("이름: 값", 표)이 실제 문서 형식을 얼마나 덮는지도 사내 기획서 표본으로 확인해야 한다.

텍스트 기반 유사도 검색은 임베딩 모델을 어디서 돌릴지(transformers.js로 브라우저에서, 또는 Ollama 같은 로컬 서버) 정해야 해서 v1 이후로 미뤘다. 대용량 파일(수백 MB 이상)에서 DuckDB-WASM 메모리 한계는 실제 파일로 측정한 뒤 정한다. 대시보드 자동 새로고침 주기도 아직 정하지 않았다.
